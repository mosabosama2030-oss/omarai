# قاعدة بيانات Omarai — SQLite محليًا وPostgreSQL عبر Neon

## القرار المعماري

- **التطوير المحلي والاختبارات العادية:** SQLite افتراضيًا، دون الحاجة إلى خدمة خارجية.
- **الاستضافة:** PostgreSQL مُدار، ويمكن استخدام Neon. يختار التطبيق هذا المحرك عند ضبط `OMARAI_DATABASE_URL` أو `DATABASE_URL`.
- **GitHub:** يحفظ الكود والاختبارات والوثائق فقط؛ لا ترفع ملف SQLite، أو نسخة احتياطية، أو عنوان اتصال، أو بيانات عملاء.
- **عزل المستأجرين:** تبقى المفاتيح الفريدة والاستعلامات المقيدة بـ`tenant_id` جزءًا من التصميم في المحركين.

## الإعداد المحلي

عند عدم ضبط متغير قاعدة بيانات، يستخدم Omarai المسار الافتراضي:

```text
~/.omarai/omarai.sqlite3
```

يمكن تغيير المسار بمتغير `OMARAI_DB_PATH`:

```bash
export OMARAI_DB_PATH="$HOME/.omarai/dev.sqlite3"
python -m cli.omarai serve
```

لا تضبط `OMARAI_DB_PATH` بالتزامن مع عنوان PostgreSQL؛ يرفض التطبيق هذا التعارض بدل اختيار قاعدة بصمت.

## إعداد Neon للاستضافة

1. أنشئ مشروع PostgreSQL في Neon واختر المنطقة الأقرب إلى تطبيق الاستضافة قدر الإمكان.
2. افتح قسم الاتصال في لوحة Neon واختر عنوان PostgreSQL عبر **pooled connection** لاستخدام عنوان pooler، خصوصًا أن التطبيق يفتح اتصالًا قصير العمر لكل عملية تخزين.
3. انسخ عنوان الاتصال كاملًا من Neon، وتحقق من وجود `sslmode=require` في العنوان.
4. افتح إعدادات المتغيرات/الأسرار في خدمة الاستضافة، وأضف متغيرًا سريًا اسمه `OMARAI_DATABASE_URL` وقيمته عنوان الاتصال.
5. اترك `OMARAI_DB_PATH` غير مضبوط حتى لا يحدث تعارض.
6. أعد تشغيل/نشر الخدمة عبر مسار النشر الذي يوافق عليه مالك البيئة، ثم راجع `GET /api/health`: يجب أن يعرض `storage.backend=postgresql` و`storage.database_url_configured=true` من دون عرض العنوان أو كلمة المرور.
7. هذا الفحص يعرض اختيار المحرك وإعداد عنوان الاتصال فقط؛ لا يثبت خطة Neon أو سياسة النسخ الاحتياطي أو استمرار الاتصال بعد بدء التشغيل. نفّذ اختبار قبول محميًا بعد التهيئة مع بيانات اختبار غير حساسة.

لا تلصق عنوان الاتصال في محادثة، أو Issue، أو PR، أو سجل CI، أو ملف `.env.example`. لا تضعه في GitHub Actions Secrets إلا عندما تكون هناك حاجة واضحة لعملية CI تتصل بقاعدة محددة؛ اختبارات CI الاعتيادية تستخدم PostgreSQL مؤقتًا داخل runner ولا تحتاج سر Neon.

## اختيار المحرك

| الإعداد | المحرك |
|---|---|
| لا يوجد `OMARAI_DATABASE_URL` ولا `DATABASE_URL` | SQLite افتراضي |
| `OMARAI_DATABASE_URL` مضبوط | PostgreSQL |
| `DATABASE_URL` مضبوط دون المتغير المخصص | PostgreSQL |
| عنوان PostgreSQL مع `OMARAI_DB_PATH` في الوقت نفسه | خطأ إعداد واضح؛ يجب اختيار أحدهما |

## المخطط والاختبارات

- عند بدء التطبيق، ينشئ `LeadStore` الجداول والفهارس المطلوبة إذا لم تكن موجودة.
- ترحيل SQLite القديم (مثل نقل جدول leads legacy إلى جدول tenant-scoped) خاص بمحرك SQLite؛ لا يُنفذ على PostgreSQL.
- سير عمل GitHub Actions يشغل اختبار PostgreSQL ضد خدمة مؤقتة PostgreSQL 16؛ لا يتصل بحساب Neon ولا يحتاج أسراره.
- اختبارات التكامل تغطي تمييز السجلات بين المستأجرين، منع التكرار، تحديث الحالة، الرموز، الجلسات، ملفات المنتج، وسجلات الاكتشاف.

## البيانات المحلية الحالية ونقلها

**لا يوجد نقل تلقائي للبيانات المحلية إلى Neon في هذا التغيير.** ملف `~/.omarai/omarai.sqlite3` يبقى كما هو على جهاز التطوير؛ قاعدة Neon تبدأ بقاعدة فارغة وجداولها الجديدة. لا تضع عنوان Neon في بيئة محلية تتضمن بيانات إنتاجية قبل وضع خطة نسخ احتياطي/ترحيل ومطابقة عدد السجلات، ولا تحذف ملف SQLite الأصلي بعد النسخ.

قبل نقل بيانات قائمة، يلزم إجراء منفصل يتضمن:
- نسخة احتياطية متحقق من سلامتها.
- أداة تصدير واستيراد واعية بـ`tenant_id` والعلاقات والمفاتيح الفريدة.
- dry-run يطابق الأعداد والمفاتيح قبل الكتابة.
- اختبار قراءة وتحديث وعزل مستأجرين على قاعدة الهدف.
- خطة رجوع لا تمس المصدر.

هذا الإجراء غير مشمول في دعم PostgreSQL الأولي.
